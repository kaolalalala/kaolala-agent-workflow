# 09 工程化、平台架构、安全与部署 (Engineering & Deployment)

本章探讨从“玩具实验室”走向“抗得住百万并发和防止黑客偷家”的基石。在商用落地的视角下，模型智商再高，如果不去治水、修堤防、做 DevOps 自动化和安全沙箱，这也只是一颗定时炸弹。

---

## 初级问题 (Foundations)

### Q1（初级）在做 AI Agent 系统的初期，很多团队会选择极其老套保守的“单体应用 + 本地数据库（如 SQLite）”，而不是一上来就采用炫酷的微服务分布式架构。为什么？

**考察点**
- 评估候选人是否具备“技术服务于阶段”的成熟克制（Pragmatism）思想。
- 单体与分布式的边界权衡。

**参考答案：收敛变量与极限闭环**
微服务并不是任何时候的万灵药，过早分布式是创业团队的催命符。
1. **初期极度缺乏边界**：Agent 的 `Workflow`、`工具链`、`评测框架` 在探索期是强行耦合在一起改动的。如果一上来拆成微服务，一个小小的 Prompt 结构改动，需要协调 3 个服务的 RPC 接口变动，迭代速度直接瘫痪。
2. **状态共享黑盒**：在单体架构里，大模型的每一步上下文都共享在一块内存或库里，报错了顺着调用栈一眼就能排查。一旦变成分布式网络，排查它为什么陷入死循环将变得极其恐怖。
所以我们要先用单体快刀斩乱麻，把“流程跑通、能力惊艳”闭环；等到要处理队列拥塞或大客户租户隔离时，再去动刀拆服务。

### Q2（初级）作为负责研发 Agent 平台的前后端接层人员，你认为客户的 API Key、数据库密码等敏感调用凭证，到底应该存在哪条链路里？

**考察点**
- 云安全的底线常识。
- 对于前台发请求的攻击面防护。

**参考答案：物理封存在大后方的地牢里**
这是红线题，**无论如何绝不能存在前端（React/Vue）代码里，也不能出现在发给大模型的那大段 Prompt 明文里！** 前者会被扒源码盗刷让你倾家荡产，后者会因为模型突然发神经而把它当聊天内容泄露。

正确的链路：
1. **环境变量与保险库**：密码保存在后端的 `.env` 中，或者极度严谨地存入云商的 **密钥管理系统（KMS / HashiCorp Vault）**。
2. **代理代填 (Proxy Injection)**：前端发送到后端的仅仅是“工具编号”。后端平台底座接收后，从保险箱拉取密码，由底座平台带着密码在内网或反向代理池中代替 Agent 去发起请求。Agent 乃至大模型到死都只知道结果，绝不触碰密码本体。

## 中级问题 (Intermediate)

### Q3（中级）平时在你们公司内网电脑上（本地环境）跑得如丝般顺滑的 Agent 脚本，一旦你把它部署到云服务器（如阿里云、K8s 集群）后，经常会遭遇离奇的断连失败。罪魁祸首是什么？

**考察点**
- 云基础网关建设与 AI 工作负载的网络冲突。
- Nginx 反向代理特性。

**参考答案：阻击长连接的网关杀手**
本地顺滑是因为它是纯内部的直接通行。一旦上云：
1. **反向代理的超时绞杀（Nginx / LB Timeout）**：
   Agent 在做长考或者爬取大网页时，经常十几分钟不吭声。而云厂商默认在网关前置 Nginx 或 LoadBalancer 设定的存活期通常非常严酷（比如 `proxy_read_timeout 60s`）。只要到了 60 秒拿不到 HTTP 返回，云网关就会冷酷无情地切断连接并报 `504 Gateway Timeout`。
2. **进程调度与会话失忆**：
   如果你把 Agent 的记忆图谱存放在 Node.js/Python 的内存条里。上云后如果是多实例部署（如 3 个容器负载均衡），用户刷个网页重连打到了第二台机器上，系统当场失忆崩塌。
解决路径必须是：拉长网关超时配置、启用无阻断 WebSocket 流式下发，并将所有的 State 记忆写进强一致性的高频 Redis 集群里。

### Q4（中级）大家都在探讨架构时，Agent 工作流系统究竟更适合部署在 Docker/Kubernetes (K8s) 制式阵营里，还是极受欢迎的 Serverless（无服务器云函数）架构上？

**考察点**
- 深度的云原生（Cloud Native）选型匹配度解析。
- Agent “重状态多长链接”的物理特性剖析。

**参考答案：重器不适合轻骑兵阵地**
AI Agent 是典型的 **“长连接 + 极强状态 + 突发高频外调 I/O”** 的怪异综合体负载。
- **推荐常驻的容器 K8s**：它能从容地维持 10 分钟以上的极长 Web Socket 以把思考流推给前端，且在执行长时间规划中能把上下文挂载在当前物理进程的高速内存中，非常安稳。
- **排斥纯正的 Serverless (如 AWS Lambda)**：
  因为 Serverless 是按毫秒计费并且用完即杀。它的冷启动极慢会破坏用户提问体验；最致命的是，很多无服务器云函数写死了“最高 15 分钟强行断电退出”的紧箍咒，对于那些要去干两个小时大数据拉取的重型智能体，这是毁灭打击。

## 高级问题 (Advanced)

### Q5（高级）如果让你把目前的“单体小平台”重构为支持大量 B 端公司同时注册并隔离使用的“企业真级大规模 Agent 平台”，你会设定怎样雷打不动的三阶段演进路线计划？

**考察点**
- 宏大架构重构下的演进路径蓝图刻画。
- 业务不挂前提下做基础建设的渐进式过渡。

**参考答案：不停机造桥的三段论**
如果一次性推翻全干，研发线必死无疑。稳妥的军工级路线应分为三极递进：
- **第一阶段：多租户逻辑隔绝与权限大闸（The Gates）**。在代码完全不拆堆堆里，把数据库底座加上租户 ID（`tenant_id`）。在平台建立大角色管理（RBAC），解决不同部门看不同数据这最大的商业卖点，把计费接口先埋好。
- **第二阶段：削峰填谷与剥离异步心跳（Message Queue & Workers）**。把大模型长推理从前台 Web 服务器里解耦生剥。前台收到了只抛弃进 Kafka/RabbitMQ。然后单独启动一批纯正的无脑苦力 Node 节点只负责跑大模型计算，算完写库。解决前段卡死雪崩。
- **第三阶段：资源物理切断隔离与大流量调度治理（MicroVM & Policy）**。最后一步才是最高端的护城河。对于那些大客户，或者支持在平台里跑未知定制脚本的功能，通过底层基建在服务器开辟基于 K8s 或极度安全的微核（Micro-VM）专属隔离带（跑一次废弃一次），保障最彻底的 CPU 计算限制和物理不串号。

## 进阶硬核问题 (Expert)

### Q6（进阶）在现代 DevOps / MLOps 理论中，建立一套保障带有巨大不确定性的 Agent 系统不断进行发版迭代的自动流水线门禁（CI/CD Gates），它的地狱级难点在哪？请描述最硬核的把控方案。

**考察点**
- 对全生命周期的自动化防控。
- 模型非确定性（Non-deterministic Regression）与代码红灯的冲突对齐。

**参考答案：黄金基线与影子发布阵线**
**最大难点：** 传统软件你测试用例如果输出等于 `3.14` 那就是成功。但大模型的输出千变万化，你改了一行核心词或者引入一个新的搜索工具，很难用传统的 Assert 去判别它的结果有没有因此跑歪智障退化。

**破除地狱级屏障的流水线架构：**
1. **结构语法死门禁 (Deterministic Syntax Check)**：不管是工作流拓扑有回路，还是新加的 Tool Schema 缺关键必填属性，静态代码引擎在流水线上直接将其判死打回，杜绝拼写故障上主线。
2. **黄金沙盘回溯拦截 (Golden Pipeline)**：拉起 500 个包含了公司史上遇到过的各种极其古怪长尾错题的基准测试集。在 Jenkins 里强制利用 CI 算力把它全部走一遍，并利用我们部署的高阶法官模型（LLM-as-a-judge）通过 RAGAs 框架去测算：相比上一版本，如果这一版的*工具调用精确度、幻觉偏离度*下滑哪怕 2%，则 DevOps 将无情触发 `Build Failed` 中断发布。
3. **线上静默阴影测试 (Shadow Traffic)**：如果是动到了主控 Meta-Agent 的根基逻辑。在真实机房的网关层复制主链路 `1%` 的真实客户进线流量转到隐蔽的新机房偷偷模拟跑一轮，将新老两方的响应差距和打点落库。如果不串台不雪崩，再做灰度放量（Canary Release）。

**💡 超越点 (Tech Lead 视界)**
“很多半吊子平台因为省事，改完一个极关键的规划算法只在界面瞎点十几下就敢推上线。但在我执掌的技术部里，我们搭建这套被我们称为 **‘飞轮防御哨兵’** 的 DevOps 系统，本身其复杂程度甚至超越了 Agent 开发本身。这就是我在面试中一直对候选人强调的：写跑得通的 Demo 是个人都会；但把这种能说废话、胡思乱想的 AI 装入能够大规模日夜轰鸣却始终严丝合缝的履带机床，才是我们要做的艺术。”
