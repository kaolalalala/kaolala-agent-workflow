# 05 RAG、知识接入与信息获取

本章重点考察你在面对“大模型知识库外挂脱节、幻觉频发”时的系统设计嗅觉。低级工程师只会调 LangChain 的 Loader 去切分和嵌入，而高级架构师关注的是 **“混合检索路线、版本控制孤岛与跨知识源冲突消解”** 的数据治理体系。

---

## 初级问题 (Foundations)

### Q1（初级）什么是大模型的 RAG（检索增强生成）？在 Agent 系统里它到底是为了解决什么痛点？为什么不直接把所有维基百科塞进 Prompt 里？

**考察点**
- 深刻理解大模型的“知识截断”和“幻觉”局限。
- Token 窗口极其昂贵的三维常识。

**参考答案：痛点与边界**
RAG（Retrieval-Augmented Generation）简单来说，就是“大模型在开口说话或者下决策之前，先帮它去数据库里‘翻书抄答案’”。
它解决了大模型的三大致死弱点：
1. **知识截断与无法更新**：模型的知识停留在训完的那一天（连昨天的股市都不知道）。RAG 可以让它接入实时的私有知识和外部新闻网络。
2. **严丝合缝的幻觉克星**：如果不做 RAG 去问它生僻概念，模型绝不闭嘴，它大概率会开始“胡编乱造”（做梦）。而 RAG 可以通过提供确切证据（Evidence）将其勒马。

为什么不一次性塞满：
1. **Token 开销等同于破产**：把 1G 的维基百科塞进去，一次对话光是发送成本就要上万元。
2. **Lost in the Middle 认知淹没**：就算塞进去了，它的智商也会被漫长的噪音稀释得连一加一等于几都看不懂。RAG 就是为了“只挑出与当前问题最相关的几句话”精准喂食。

---

### Q2（初级）什么是 Chunking（长文本分块切片）？为什么如果在 RAG 的地基里没切好，上面所有的检索效果都会极度拉胯？

**考察点**
- 评估候选人是否动手做过原始数据的预处理。
- 文本语义密度的物理常识。

**参考答案：基础工序的底盘**
把一本 500 页的《劳动法》PDF 书整合成一个 Vector Token 向量是荒唐的。因为整本书混合了无限复杂的知识点，它的特征向量最终就会变成一张四不像的泥沼，永远无法在用户问某一条微小细节时匹配成功。
**Chunking** 就是用“分词器、段落换行符甚至标点符号”，硬把这头大象切成类似于“300 字一段”并且“前后重叠（Overlap）50字”的肉块（Chunks）。
每一块代表一个聚焦的知识原子。如果你切得太巨大，一问等于没问（召回大量无关信息）；如果你切得太碎小（比如半句话为一个切片），虽然由于关键字对撞召回率高，但拼接进组装上下文时，前因后果尽失，模型完全看不懂半句断言是什么意思。

## 中级问题 (Intermediate)

### Q3（中级）什么时候该把知识做给当前节点（Node Context），什么时候该用全局搜索工具（Search Tool），什么时候用长期记忆库（Vector Store）？如果搞混了会出现什么灾难？

**考察点**
- “知识源”分层治理的思想（路由学）。
- 知道静态事实、瞬态网络事实、长期沉淀经验的区别。

**参考答案：知识溯源与多路界定**
如果所有的信息找寻都走 RAG 向量大库，系统就会出现反应极慢并且“信口雌黄拿去年过期数据作答”的灾难。真正的系统架构必须对信源分而治之：
- **当前节点 Context (系统级常数)**：绝对不会随时间改变的标准法则。比如“你必须遵守阿西莫夫机器人三大定律”、“本公司的核心发票税号为 911”。这必须刻在静态资料里跟着 Prompt 走，不要浪费时间去查库。
- **搜索工具 (实时探测触须)**：对于“苹果今天发布的新车配置”、“目前我账户的可用余额”，应该给 Agent 开具类似 `serpapi` 或 `sql_query` 的实时工具接口权限强制去跑，绝不可查大库旧文。
- **长期记忆 Vector RAG (跨时代的经验沙盒)**：适合沉淀“上回客服是如何安抚大客户怒火的话术”以及几万页不可穷尽的“产品说明书疑难杂症”。

### Q4（中级）在检索后组装上下文时，什么是 `Top-K`？为什么很多菜鸟为了追求“宁可错选绝不漏掉”而把 K 值设置得极大（比如20），结果反而导致最终回答质量惨不忍睹？

**考察点**
- “知识倒灌”对于 LLM 规划与逻辑树的影响。
- RAG 构建中的噪音容忍度。

**参考答案：倒灌与智灵失焦**
**Top-K** 指的是，底座向量计算出相似度得分后，只向大模型呈递前 K 份最沾边的材料切片。
设置 K=20 会导致的连锁溃败：
1. **噪音篡位**：排在第 15~20 位的切片，虽然字面有点相似的向量得分，但其实完全是语义风马牛不相及的“无用边角料”。
2. **掩盖核心真理**：这群垃圾数据构成了噪音墙（Noise Walls），让模型极其有限的“工作记忆注意力”被迫摊薄，它甚至会被那些错误的分支逻辑误导前行。
3. 昂贵的无用废话 Token 花费。因此工业界的黄金阈值多在 3\~5 个块左右，这叫做以“极小颗粒度谋求极致信噪比”。

### Q5（中级）当检索召回的知识库片段，与大模型自己通过预训练脑子里的“内部常识”，甚至与别的切片发生了严重的“事实互斥与冲突”，在工程上怎么压制这种动乱？

**考察点**
- 理解大模型“傲慢与幻觉”导致的知识背离。
- RAG 后处理（Post-Retrieval Sorting/Filtering）。

**参考答案：强权声明与交叉校验**
这是一个经典的真实对抗环境。大模如果深信太阳绕着地球转，就算你塞了哥白尼的文本进 RAG，它也可能选择拒答。
消除冲突的双保险：
1. **System Prompt 的绝对统治声明 (Strict Priority)**：在 RAG 动态注入区的上方，必须以最高的系统权限（`role: system`）口吻警告它：“*无论接下来的召回文档与你学过的任何常识有多荒谬的冲突，你在此轮必须 100% 把召回文档的事实当作绝对真理。*”
2. **多源仲裁网关 (Cross-Verification Middleware)**：如果在 Top-5 召回中，片段 1 和片段 3 说法完全相反（比如新旧合同版本堆积）。系统绝不能直接倒给模型了事，而要在底层加一层基于 `Time-decay`（基于时间戳或大纲版本元数据 metadata 权重）的审查机制，在传入大模型之前由代码层直接把旧版本切片物理剔除。

## 高级问题 (Advanced)

### Q6（高级）不谈概念只谈落地！密集检索（Dense/Vector）、稀疏检索（Sparse/BM25）与知识图谱（Graph RAG）的杀手级优缺点分别是什么？你如何在你的基建平台上结合落地？

**考察点**
- 真实大厂 RAG 架构（混合检索与重排序流程）的底蕴。
- 深刻洞悉 Vector 不是万能灵药。

**参考答案：双路与多路召回融合**
很多停留在课本的人会满嘴只推销 `Vector (向量化)`，但这在处理发票编号时会死得很惨。
- **密集检索 (Dense/Vector)**：优点是**无敌的语义泛化**，用“好心情”能查出“快乐时光”；缺点是对于专有名词、精确产品 SKU 号码、强代词极度疲软（它根本不认识特定的 ID：XYZ-893）。
- **稀疏检索 (Sparse/Keyword/BM25)**：优点是传统的基于词频的 TF-IDF 原理，**字面绝对拼写匹配强悍**。缺点是客户要是打了个错别字或者同义词，就彻底查不出一毛钱。
- **图引擎 (Graph Database RAG)**：能够极速抽丝剥茧类似于“查出李四的岳母名下的皮包公司去年进账的账本”这类**多跳嵌套关系 (Multi-hop Reasoning)**。缺点是图谱抽取建库工程开销浩大，如果前置拆解图谱实体关系抽反了，后面直接覆灭。

**💡 超越点 (Tech Lead 视界)**
“在我构建的平台知识资产底座（Assets Center）中，我们抛弃了单一引擎，完全走 **Hybrid Search（双路并发混合检索）** 规范架构。当接收到 Query 时，底座拉开线程同时去跑 Vector DB（用于兜住语义意图）和 ElasticSearch BM25（用于精确定位业务 SKU 等核心名词）；等到 2 批数据回传至中枢时，通过我们调优的 **RRF（倒数排名融合算法）** 重新洗牌与倒排。这就是我们拿业务高压测试锤出来的护城河。”

## 进阶硬核问题 (Expert)

### Q7（进阶）在发版或者更新知识库时，怎么在全自动 CI/CD 系统里用数学或工程证明你的这一次庞大的知识 RAG 接入“真的让 Agent 智商变高了”，而不是“引狼入室让它满嘴喷垃圾堆噪音”？

**考察点**
- 顶层系统可观测监控 (Evaluation Pipelines)。
- A/B 测试基准和 RAG 回归防退化设计（RAGAs）。

**参考答案：基于裁判管道的黄金断言防线**
绝大部分草台班子加了知识库只会在控制台“盲问”几个 Case 并心满意足发布，结果线上立刻发生大规模的牛头不对马嘴灾难。如果要做可维护的企业级基建，必须要上“自动化防暴雷验证闭环（Evaluation Pipeline）”。

要验证这不仅仅是复杂度的徒增，而是真金白银的收益，必须过检测流水线：
1. **控制变量对拼法**：我们有一套多达千题的 “黄金 Benchmark 回放靶场”。系统会在后台发起无 RAG、仅静态文档 RAG、搜索 RAG+长期记忆的三股对照组（Baseline Comparison），强发测试集并抓取。
2. **评价指标的分层解剖**：不只是看回答好不好。我们会用诸如引入了 GPT-4 作为冷酷法官（LLM-as-a-judge），评测：
   - *Context Precision（上下文查准率）*：你召回进来的长篇大论里确实含答案吗？
   - *Answer Faithfulness（回答忠诚度）*：最终回答是不是在造反瞎编，还是严丝合缝地基于了召回？
3. **延迟与代币账本硬性比较**：如果这套新的混合重排架构将 `Latency（延迟）` 拉长了5秒钟并且 Token 开销翻倍了 4 倍，然而正确率仅仅提升了 1%，作为 Tech Lead 我的评价是必须砍掉回滚！

**💡 超越点 (Tech Lead 视界)**
“知识不意味着智慧。在我们平台的 `CI/CD 发版门禁面板` 中，任何新外接的知识簇，如果不在这条管道中把 `Recall` 和 `Faithfulness` 的绿色打分条顶破历史基线的 `P90` 分布柱，我们底层那套 DevOps 流水线会用极刑一般的强硬态度直接熔断阻遏合并，拦截这些幻觉在生产环境蔓延。”
