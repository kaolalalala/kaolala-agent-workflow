# 03 上下文、记忆与状态管理

本章专门考察系统对于 Token 和上下文窗口（Context Window）的精算能力。随着 Agent 生存时间的拉长，系统最容易死在“记忆爆炸”与“幻觉污染”上。高阶开发者明白：给大模型看的资料，绝不是简单的拼接，而是苛刻的“装配工程”。

---

## 初级问题 (Foundations)

### Q1（初级）在构建 Agent 时，如何区分“上下文窗口 (Context Window)”、“工作记忆 (Working Memory)”与“长期记忆 (Long-term Memory)”？它们之间是什么关系？

**考察点**
- 是否分得清 Context 和 Memory 的物理/逻辑界限。
- 是否理解“能存下来在库里”和“会被当前轮次使用”完全是两码事。

**参考答案：职责划分**
很多初学者会把这三者混为一谈，导致系统每次都试图把整个数据库塞给模型。
- **长期记忆 (Long-term Memory)**：是跨越 Session 会话的存量知识池（通常落在 MySQL 或向量库 VectorDB 中）。它记录历史事实，但不一定会参与本次对话。
- **工作记忆 (Working Memory)**：是针对“当前正在推进的单次任务/Run”而临时圈定的白板区。它包含了本轮目标的初始设定、中间思考草稿和刚拉取回来的关键工具返回结果。
- **上下文窗口 (Context Window)**：这是最昂贵、最底层的物理限制。它是当前这一次 HTTP 请求真正送进大语言模型进行推理的 Token 序列封包。

**关系**：长期记忆是海量矿山，工作记忆是当前的提炼车间，而上下文窗口是运往大模型工厂的极其狭窄的高速公路。我们必须通过“检索和压缩 (RAG & Summarization)”把前两者的内容精简后挤进第三者。

**💡 超越点 (Tech Lead 视界)**
“在我设计的基建大盘中，这种分层体现在彻底的解耦上。我们专门有 `Assets Center` 管辖长期记忆，而当 `Meta-Agent` 拉起一次具体的运行任务时，会基于它构建一个自带垃圾回收的 `Context Snapshot`（上下文快照）作为工作记忆。这样既保证了长期知识的跨业务线复用，又避免了当前工作流被陈旧知识引发蝴蝶效应污染。”

### Q2（初级）当对话历史和工具返回结果塞满，导致模型报 `Context Exceeded (上下文溢出)` 崩溃时，最简单直接的急处理手段有哪些？

**考察点**
- 对于 LLM Token 计数的直接应对机制认知。
- 滑动窗口机制的底座常识。

**参考答案：物理截断与压缩**
当 Token 逼近物理上限（如 8K 或 128K）时，如果不加控制，下一次工具调用就会让引擎报 400 异常终止。最成熟的三板斧是：
1. **滑动窗口截断机制（FIFO Sliding Window）**：像队列一样，当总 Token 越界，直接把最老的、几十轮之前的寒暄记录抛弃掉。
2. **强制清洗废弃中间件痕迹**：在冗长的推理链中，大段的 HTML 工具抓取代码或巨大的 JSON API 返回物在用完后就没有价值了。及时将无用的 `Tool Response` 清空，只保留人类的指令和 Agent 的总结 `Thought`。
3. **紧急触发 LLM 算力压缩 (Summarization)**：挂起主流程，唤醒一个小模型（如 GPT-4o-mini 或本地模型），让它快速把前面几千字的对白“用一句话归纳提炼”。把几千字替换为“用户之前问了价格并探讨了物流”。

## 中级问题 (Intermediate)

### Q3（中级）为什么在企业工程里，决不能把所有查询历史和工具返回一股脑塞进 Prompt 里？大厂是怎么做“上下文装配与 Token Budget (配额预算)”的？

**考察点**
- 是否理解上下文窗口的业务隐患：除了崩内存，还会让智商退化。
- 是否具备“装配组装”和“金钱预算”思维。

**参考答案：装配工程化**
不加过滤全塞进 Prompt 会带来四大灾难：
1. 超长文本会让模型反应剧烈**降速**。
2. 费用**极其昂贵**，每一小步聊天都在为几万过去的 Token 买单。
3. **注意力分散 (Attention Dilution)**，模型会忽略当前的极高优指令。
4. **过期脏数据污染**，历史的失败结论会极大地干扰它现在的判断。

**大厂最佳实践 (上下文动态装配)**：
上下文绝不是“字符串堆料”，而是“动态装配表”。我们要给不同的信息源设置强硬的 **Token Budget（配额分配表）**。例如总计 10000 Token，保留 2000 给 System Roles，4000 留给最新的 RAG 工具检索结果，2000 留给滑动对话历史。
如果工具搜回来的数据超过 4000，底座绝不会侵占 System 规则配额，而是强行对工具数据执行截断裁切，确保系统的核心设定永不失忆。

### Q4（中级）长文本场景下臭名昭著的“Lost in the Middle（迷失在中间）”现象是什么？为了缓解它，在排版 Prompt 工作记忆时有什么讲究？

**考察点**
- 熟知主流 Transformer LLM 处理大规模语境时的注意力衰减物理学缺陷（U型衰减曲线）。
- 掌握如何用硬隔离技巧挽救系统认知溃散。

**参考答案：U型注意力陷阱**
“Lost in the Middle” 指的是：当 LLM 阅读一篇极长的文章（十万字）时，它天然对文章的**最开头（Head，含系统人设）**和**最结尾（Tail，含用户的终极问题）**保持了极高的精确注意力，但会大概率直接遗忘、无视或者瞎编位于中间断层的细则信息。

**装配排版避险策略**：
1. **夹心饼干策略 (Sandwich Encoding)**：绝对不要把规则和限制丢在中间。比如“必须输出 JSON”和“用户的任务”，必须用显式的块标签放在最前部和最后端。把大段用来辅助参考的、不那么致命的 RAG 知识库切片（Evidences）夹在中间塞进去。
2. **强制锚点引用验证**：如果我们确切依赖了中间的某段记忆（如 `[Memory Block 34]`），在系统词的末尾要求它：“你必须找出引据点的编号再作答”，逼迫模型在生成文字的解码过程中横跨注意力空间，完成自校验。

### Q5（中级）向量数据库（Vector DB）在 Agent 的“显式记忆系统”中到底扮演什么不可替代的角色？它有什么致命短板，从而决定了它不能“作为唯一的记忆存储”孤军奋战？

**考察点**
- 深刻拆分“数学语义检索 (Semantics)”与“确定性过滤 (Deterministic Filter)”的系统边界。
- 多路召回架构的设计直觉。

**参考答案：角色边界与协同**
**不可替代的角色：** 向量库充当的是**按语义意图模糊嗅探**的侦探角色。比如用户问：“上回那份聊退货的文件在哪？” 向量的 Embedding 相似度计算能跨越字面匹配，准确召回两个月前的“订单售后条例纠纷”聊天段落，这是传统 MySQL 搜索绝无可能做到的。

**不可作为唯一存储的致命劣势：**
1. **缺乏时序排列与绝对因果**：向量数据就是浮点数数组，它并不知道时间先后。如果依赖纯向量寻找“我最新的收货地址在哪”，极有可能把三年前的废弃旧地址召回而坑死业务（因为旧地址的向量分数可能只差 0.01）。
2. **无法做确定性代数过滤**：碰到诸如“帮我汇总去年花费超过 1000 元的订单明细”这种问题，向量库完全两眼一抹黑。
因此，真实的企业级平台永远是 **`Vector DB + 关系型数据库 (如 SQLite/PostgreSQL)` 采用 metadata 时态关联和双路召回**，绝不把命交在纯向量算分上。

## 高级问题 (Advanced)

### Q6（高级）把一次性的运行经历变成长期知识（Cross-Run Memory）是一件极度危险的事。如果要设计跨运行共享记忆，如何避免记忆污染与错觉雪崩（错误放大）？

**考察点**
- 评估候选人的“记忆合规治理体系 (Memory Governance)”意识。
- 是否懂得在读写两侧引入衰减（Decay）与硬隔离。

**参考答案：治理与衰减隔离体系**
跨运行记忆（把 Agent 的单次经验存回大公海池）最大风险在于：一旦某个 Agent 脑抽想错了、总结错了并落库，明天所有的下游工作流在跑相似任务时全都会吃下这份有毒甚至张冠李戴的先验错觉。这是一个指数扩散的灾难节点。
真正的系统设计必须构建**多环记忆防污网**：
1. **严苛的写回熔断 (Write-back Validation)**：系统绝不可以“无脑把所有跑过的链条都固化”。只有满足：带有显式 `Success` 结尾标记的、经过人类反馈（Thumbs up）过的、或是经过了 Evaluation Pipeline 自动化裁判得分高于 90 的 Trace 快照，才允许被萃取写入长记忆池。
2. **多租户数据作用域物理隔离 (Tenant / Workspace Sandbox)**：每一份写入都要带上隔离标签（比如该项目、该团队甚至该用户的 ID）。在做底层查询时，利用 Metadata 租户滤网卡死权限，以免项目 A 被项目 B 的噪音污染。
3. **基于时间的信用衰减体系 (Temporal Confidence Decay)**：任何旧记忆，不论当时多优越，其在召回时的权重（Ranking Score）都应该随着时间对数衰减。新的知识必须压倒去年甚至上个月的历史。

**💡 超越点 (Tech Lead 视界)**
“在我构建的全息观测面板（Runs Center）中，记忆不仅在读写时有隔离，在溯源时同样具有**微服务级别的追踪透视图 (TraceId Mapping)**。如果有一天大家发现大模型集体在某项指标发了癫，运维人员通过 Span 可以精确定位到是资源中心 (Assets) 里的哪一条长期记忆记录“带了毒”。我们只需在平台一键熔断下线该数据，全体智能体的病态立刻痊愈。没有观测，长期记忆就是慢性毒药。”

## 进阶硬核问题 (Expert)

### Q7（进阶）如果你是在做商业化的 Agent（尤其是 To-B 的金融/医疗等合规系统），从代码和网关底层如何安全强力合规地斩断 PII（个人隐私信息）被意外写入全局知识大模型长期记忆的灾难？

**考察点**
- LLM 产品真正的商业死亡底线（合规审查/商业伦理/SOC2/GDPR）。
- 脱敏/假名化系统前置网关设计。

**参考答案：红线网关拦截器**
对于工业化落地团队而言，这不仅是代码的麻烦，而是吃官司和失去投资人的法律红线噩梦。在合规环境中，如果用户的身份证号、医疗诊断书、内部服务器密码进了公共长记忆库（甚至可能出现在明天另一个客户用相近 query 问话返回的 Prompt 组装中），这叫史诗级侧信道泄漏。

工程防线必须建到底层 API 通讯关口：
1. **脱敏拦截中间件 (Masking Proxy / DLP Gateway)**：在任何 Agent 抓取的数据送达 `Vector Embedding API` 或入库落盘前，必须过一道正则引擎或轻量级 NLP 识别网关。把身份证号无情替换为加密令牌 `<MASKED_ID_342>`，确保入库的仅仅是骨架语义结构而非肉体明文。
2. **基于凭证池的双向渲染恢复 (Dual-Rendering with Key Vaults)**：如果业务真的需要在最后把数据发给特定客户查看，系统在通过安全路由时，从独立受限的金库（Vault）把令牌原路解密回去。这使得在 AI 记忆与反思推理区中，模型操作的全是加密替身（Aliasing Data），实现了端云彻底的物理切断。
