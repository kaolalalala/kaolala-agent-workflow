# 07 评测、可观测性与调试 (Evaluation & Observability)

本章是检验你是否具备 CTO/技术总监视野的试金石。因为初级玩家最关心的是“Agent 怎么写能跑通”，而真正掌管线上万级并发命脉的扛把子，最关心的是“跑崩了到底怎么查、怎么发红黑榜”。这涉及微服务级别的全息测绘与发版裁判。

---

## 初级问题 (Foundations)

### Q1（初级）为什么同样是写后台代码，Agent 系统看报错日志（Logs）比普通 Web 系统难上十倍？

**考察点**
- 深刻理解 AI 的“概率性缺陷”与确定性代码的边界。
- 黑盒观测痛点。

**参考答案：黑盒与逻辑偏航**
如果是以前用 Spring Boot 写一个发帖接口，系统报错抛出了 **`NullPointerException` (空指针异常)**，我们可以直接顺着 `Stacktrace (控制台堆栈)` 眼皮子底下在一秒内定位到具体的 `Controller.java 第 48 行` 代码去修复。因为这是确定性的。

而大模型系统是**非确定性的软逻辑**。当在线上跑出了一个极其荒谬的答案（或者是大模型开始胡言乱语），系统中没有任何一行报错抛出来（HTTP 200 OK）。你不知道它是：
1. 本身提问时的 Prompt 歧义？
2. 外挂 RAG 刚才召回了一片垃圾塞进它脑子把它染黑了？
3. 工具返回的 JSON 少了个右括号？
在没有专门建立观测系统前，排查 LLM 故障跟请法师做法无异，全靠猜。

---

### Q2（初级）什么是 Trace（完整轨迹）和 Span（动作跨度）？在咱们这行里它和传统的意义有什么区别？

**考察点**
- 对于 APM (Application Performance Monitoring) 词汇的 Agent 化对应。
- LangSmith 等商用大盘的核心概念域。

**参考答案：生命周期的解剖图**
这是从 OpenTelemetry 等基石协议中搬过来的概念：
- **Trace（一条骨骼线）**：代表“单次用户的查询指令”所引发的总生命周期。比如用户打字“帮我写个报表并保存”，这个宏观的任务从接入第一秒直到十分钟后打出“文件已保存”为止，这 10 分钟统统算在一个 Trace 里。
- **Span（骨架上的关节器官）**：Trace 里面包裹的任务碎块。
  - 在 Agent 宇宙里，Span 1 叫 `[LLM_Call: GPT-4 思考消耗 3s, $0.01]`。
  - Span 2 叫 `[Tool_Execution: Google 爬虫等待 5s]`。
  - 它们之间存在父子层层树状潜入关系。所以 Trace 和 Span 的组合，让管理者能一眼横向拉出甘特图，看清这 10 分钟到底是哪个“关节”拖了后腿。

## 中级问题 (Intermediate)

### Q3（中级）为什么在构建 Agent 平台时，系统本身比普通 API 更迫切需要内置高保真度的可观测性大盘（如 LangSmith / 平台自研 Trace Center）？

**考察点**
- “一次性交付”到“持久型诊断治理”意识的跃迁。
- 业务运营监控。

**参考答案：动态多线追溯**
Agent 不同于单向接口的地方在于：
1. **多层叠套，隐藏状态极深**：一句话进去，背后往往发生了 3 轮大模型推理，5 次工具调用。如果只暴露最终答案给客户，不仅调试灾难，更不知道中间消耗了多少钱。
2. **需要将 Token 当作金钱来计量**：系统的观测面板不仅要看输入输出（I/O），还必须从微服务级别实时统计出当前这一个子节点烧了多少 `Prompt Tokens` 和 `Completion Tokens`，然后折算为美金。一旦某个节点发生死循环，大盘必须根据监控到瞬间飙升的财务数字执行断路器杀进程，否则公司将面临灾难性账单。这是没有观测就绝对无法实行的经济红线拦截。

### Q4（中级）如果让你设计一套 Agent Evaluation（评测与计分板），光看单次生成的打分是不准的。为什么 Replay（回放重跑）和 Compare（基线对比）极其关键？

**考察点**
- 评估算法防退化控制观念。
- 回归测试（Regression Testing）的深入理解。

**参考答案：概率世界的度量尺**
如果今天你改了句 Prompt，跑了一次感觉答案“好像更顺滑了”就高兴地上线，这是极其外行的。因为大模型每次生成本来就不一样，这就是概率。

要有说服力，必须拉出一套闭环测绘（CI/CD Eval）：
1. **固定测试集与 Replay（回放拦截）**：你在平台积累了 1000 道极度复杂的黄金业务测试用例边界题（Baseline）。今天你想改底层规划器的架构，你必须用新系统重新跑这 1000 道题。
2. **Compare（基线差异对比）**：用这 1000 道题的新老输出、Token 花销打在一张两列面板上。我们只关注那些发生改变（Regression）的案例。比如：由于换了更轻快的模型，Token 费用砍了 50%，但是遇到 11 号财务难题时，它不再会正确调用计算器而是瞎猜了。没有 Compare 机制，你就永远不知道你在按下升级按钮时，又引发了哪只偏航的蝴蝶效应。

### Q5（中级）当前行业里特别流行的一种评测叫 “LLM-as-a-Judge (大模型当法官)” —— 即让 GPT-4 去给其它模型的产出打分。它的致命缺陷是什么？如何在这套系统里兜底？

**考察点**
- 对新兴学术及开源 Eval 方法的落地踩坑经验。
- “纯感性评分”与“绝对红线”的冲突。

**参考答案：裁判眼瞎与自嗨病态**
我们确实常常用最贵的模型去评估便宜模型的打分。但它也有致命的病灶：
1. **自我偏好与格式宽纵 (Self-Enhancement / Loose Checks)**：它经常对长篇大论但信息稀薄的回答打高分；极其糟糕的是，如果你让它检查一段代码能不能跑、一个 JSON 是否缺了逗号，它常常会因为“看着眼热（大概齐差不多）”而给予放行。
2. 兜底法则是引入 **混合评测门禁（Hybrid Metrics Pipeline）**：
   我们绝不会把判决权全交给 LLM。比如一条指令流：先过**物理代码测算层（Deterministic Eval）**（JSON 反序列化一遍看报不报错、执行沙箱里跑一下 `pytest`），物理层一旦返回 0 直接挂红灯无需讲理；只有物理检查通过，才把结果送到 LLM 裁判的手里，让它去评价这段过检的代码**是否优美、是否遵循人设语气（Open-ended Specs）**。这就是“感性之前先严守理性”。

## 高级问题 (Advanced)

### Q6（高级）好，实战演练！线上报警，有客户投诉你的生产级 Agent “刚才这笔财务流转算出来的总数不对且胡言乱语”。作为平台负责人，请描绘你从头排查的诊断链路，如何排除 Prompt、Tool、Workflow、Memory 及大模型底座提供商（Provider）的层层嫌疑？

**考察点**
- 高级排障方法论与心智模型。
- 是否具备严谨的从底向上的归因排查体系。

**参考答案：剥洋葱式分层追溯**
没有受过正规训练的人上来就去乱调一通 Prompt，而正派工程师的底盘排查链如下：
1. **网络层与 Provider 层探针**：点开 Trace Dashboard，第一眼先看当前时间轴上到底有没有泛红的 `Span Fallback`。是不是 OpenAI 刚才崩了切到了本地备用烂模型？或者是因为限流（Rate Limit）导致返回包失真？（如果是，跟应用本身无关，是基础设施波动的锅）。
2. **控制流编排层 (Workflow Routing)**：看图表里的路径连线对不对。如果原本该走向财务清算的，被错误路由到了“客服聊天”节点。那问题就不在 Prompt 里，而是 Router 节点条件判别边（Edge）的阈值卡错了。
3. **工具拦截层 (Tools Execution)**：如果在计算节点，点开它的那一个局部 Span 的参数 Payload。是模型下给工具的 JSON 就已经带错了数字（Prompt 问题），还是明明下对了、但因为调用 Python 时超时未返回而被强制赋了个 `null` 导致结果崩溃（工具沙箱问题）？
4. **最后：记忆装配池 (Context Memory Mount)**：最后一步才看送到模型嘴边的那一长串完整上下文，有没有把昨天别人那条相似但不相关的账单数据给拉取了进来产生“跨行污染”。排除所有物理异常后，你再去调教 Prompt 指令微调优化逻辑。

**💡 超越点 (Tech Lead 视界)**
“如果不加约束，这五层的排查在一团乱麻的 JSON 纯文本日志里可能要找一宿。所以我们在基建上利用规范的 OpenTelemetry 协议在全平台上游布好了天罗地网，一键生成带着时序热力图的瀑布分析板。当我们排障时，我们不用猜是哪一层，我们是让数据面板的红绿灯直接教我们去哪一层写补丁，这就是全息监控平台的核威慑力。”

## 进阶硬核问题 (Expert)

### Q7（进阶）当你的大平台支持横跨几十个微服务宿主的并发波次运作（宏大的任务横跨多个独立子 Agent 例如 Web Crawler, Code Executor, Summary Engine），在多台异构物理机上发生产出传递，你如何设计一套底层架构，避免在并发下各机的 Trace 完全撕裂拉配不齐？

**考察点**
- 大基建微服务架构与大模型异步任务绑定的世界级难题探究。
- 携带式 Trace 上下文跨进程传输（Context Propagation）。

**参考答案：全局封套与分布式沾染**
如果在单一脚本里，一个 `TraceId` 往下传很容易。但当任务裂变成海量并行的 **Waves（并发波次）** 并下发到不同容器时，常规的 Agent 框架日志就会变成不同机器上各说各话的乱码碎纸机。

核心分布式透传解法如下：
1. **统一的 Trace 上下文封信头透传（Context Propagation Injections）**：从总控调度面（Meta-Agent）接到初始请求的第零微妙，生成一颗宇宙级的 `Root Trace ID` (如 `UUID-8864`)。
2. **在所有网络出关口下发伴随协议**：不管是通过 HTTP 调用外部爬虫，还是把代码发送给隔离沙箱 Docker 跑，亦或是下发进 Kafka 队列。在框架的最底端网络库中强制切入拦截器（Interceptors），将这个 `Trace ID` 和它当前所属节点的 `parent_span_id` 强行塞在 HTTP Header（例如 `X-B3-TraceId`）或者事件信封（Message Envelope Metadata）中发往天下。
3. **终极多路复用吸纳（Stream Multiplexing Sink）**：远端的沙箱 Agent 开工前，必须先吃下这个被沾染的标记；等它完工或者把进度推回到 WebSocket 返回状态机中心时，带回同样的标记封套。最后，平台面板利用这个全局唯一标识进行“连连看”图谱重组，将被拆解在几十台机器上的波次重铸为一棵壮观的单树干发散回收入库图。

**💡 超越点 (Tech Lead 视界)**
“这就是我在咱们 Agent 平台实现最引以为傲的底层重器。利用这种级别的分布式沾染重铸，当我们的前端在呈现流式输出打字机特效时，底盘里其实汇聚了不同服务并发推送回来的不同线程的结果（Multiplexing），但由于每一个信封都有这枚 ID 邮戳，哪怕返回得再乱序杂乱，前端也能分毫不差地解包，分拣推入 4 个独立小 Agent 的视图框里。在监控领域叫追踪，在应用工程上，这叫做并联世界线归一。”
