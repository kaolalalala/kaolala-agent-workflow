# 01 基础概念与 Agent 系统认知

本章考点属于“道”的层面，主要评估候选人是否摆脱了“大模型调用员”的认知局限。高级的面试往往从这些看似“假大空”的问题切入，借此摸清你是否具备**建立复杂控制循环**与**治理非确定性软硬件系统**的底层设计哲学。

---

## 初级问题 (Foundations)

### Q1（初级）什么是 Agent？它和普通聊天机器人、脚本自动化有什么本质区别？

**考察点**
- 是否真正理解 Agent 的最小工程定义。
- 是否知道“模型能力”和“系统能力”不是一回事。

**参考答案：理论与对比**
一个工程意义上的 Agent，绝不只是“挂载了外接知识库的聊天系统”，而是一个**围绕既定目标，能够自主规划、行动并在失败中自我更正的活体循环系统**。
- **与聊天机器人的区别**：聊天机器人是单向函数 `Response = f(Prompt)`；Agent 是包含内部闭环的时序状态机，它有自我维持的 Loop。任务一旦交由 Agent，它可能在你没有干预的情况下独自跑半小时。
- **与传统脚本自动化的区别**：传统代码（如定时的 Bash 脚本）是 100% 确定性的。如果中途某个 API 改名或者返回结果偏差，传统脚本必定崩溃（Except Node）；而 Agent 用大模型作为“柔性解析引擎”，理论上它能容错并在一定程度上自理修复。

**💡 超越点 (Tech Lead 视界)**
“在我参与主导设计的 Agentic OS 架构中，我更愿意称呼 Agent 为一个**具有容错弹性的异步软进程**。在我们的 `Runs Center` 大盘中可以看出，它的本质不再是被动问询，而是利用大语言模型的自然语言理解力作为 `Router`，在底层的工具池中像一个水手一样自己寻路找答案的过程。”

---

### Q2（初级）Agent 在运行过程中为什么极容易出现“幻觉”以及跑飞？

**考察点**
- 理解 LLM 的概率生成本质。
- 是否明白“未加围栏的 AI”是炸弹。

**参考答案：根因剖析**
大语言模型本质是一个巨大的概率机：预测“接下来哪个词（Token）出现的概率最大”。
所以它之所以会产生幻觉（比如自己编造了一个根本不存在的 HTTP 接口去跑去请求调用）：
1. **训练数据噪音陷阱**：遇到未见过的长尾任务边界（Corner Cases）时，模型没有答案，只能本能地开始“做梦”（如输出一段虚假的 Python 路径）。
2. **缺乏多模态/真实反馈**：如果不加外部的确定性校验，它自己并不知道自己发出去的参数是否符合 JSON 标准。

**💡 超越点 (Tech Lead 视界)**
“大模型必然有幻觉，这是由它的底层物理学决定的。试图把 Prompt 写得如天书般复杂来消灭幻觉，是徒劳的。在我的平台里，我用极度变态的**底层硬工程**去约束它——只要我平台的 Schema 解析器发现模型返回的工具参数不对，我的**熔断器 (Circuit Breaker)** 组件会在毫秒内截停它，抛出错误让它当场重做，这就是我给幻觉套上的项圈。”

---

### Q3（初级）你认为哪些场景根本不需要考虑引入 Agent？

**考察点**
- 评估候选人的“技术克制能力”。不为了炫技而强上大模型。

**参考答案：避坑原则**
在架构设计时，应当遵循这个原则：“能用确切 if-else 代码解决的，坚决不用大模型。”
- **高度结构化的内部流转**：比如税务账单的格式转换与加减乘除、日终对账单的导出统计。
- **延迟要求在 200ms 以内的实时交易系统**。
- **高危且不可撤回的红线操作**：比如没有人类“在环（Human-in-the-loop）”的情况下，自动给公司开除人、或者执行超高权限 Drop 数据库指令。

## 中级问题 (Intermediate)

### Q4（中级）一个最小可运行的 Agent OS（智能体操作系统），其核心的系统架构模块到底长什么样？

**考察点**
- 是否具备现代微服务与分布式系统的拆分意识。
- 是否能从基建（Infra）角度而不是“调用员”角度回答问题。

**参考答案：系统模块拆包**
普通的开发写一个单文件 Python 脚本就能跑。但在工业级交付标准下，我们要落成微服务级的能力，至少切割为五大神行组件：
1. **统一资产隔离池 (Assets Center)**：不能在代码里硬编码 Prompt 和外接工具。而是提取为高度可插拔配置的 Tools, Prompts Schema。
2. **规划与路由大脑 (Planner / Meta-Agent)**：系统主控控制面，负责动态任务下发、进度重评估和将死胡同的任务废弃重置。
3. **长期与短期记忆中心 (Memory Storage)**：不仅要有 Session Context 短时记忆，还要有跨会话能够固化用户偏好或者环境参数的长期记忆系统（如 RAG 向量池）。
4. **工具驱动台 (Runtime Executor)**：它包含网关，代理请求、权限隔离（Token 管理）沙箱。
5. **观测大盘 (Trace & Runs)**：任何没有系统级追踪的 Agent 都是定时炸弹。必须要完整的链路 Span。

**💡 超越点 (Tech Lead 视界)**
“在我从零发起的智能体平台中，我发现这五大神兽里面，真正最难、而且决定系统能跑多远的其实是 **‘执行层的引擎重组’ (Runtime Orchestration)**。传统的脚本死等返回效率太低，我利用 Node.js 的事件流写了一套 **波次并发 (Parallel Wave)**，把无依赖的查询通过 `Promise.allSettled` 一口全部推出去执行，将总耗时狠狠压榨了 60%。”

### Q5（中级）如何为 Agent 系统设计“休止符”与终止条件 (Termination)？为什么它生死攸关？

**考察点**
- 防破产（Loss Prevention）理念实操。
- 设定安全卫士与降级兜底的工程习惯。

**参考答案：安全边界管控**
没有终止条件的 Agent 等同于不受控的信标，如果陷入逻辑黑洞，它会不停地虚耗计算资源，直到把大模型提款机刷爆。
终止条件的标准做法：
1. **显式主观达成判定**：模型需要在自己的状态机参数中，用结构化 JSON 输出一个类似于 `{"status": "FINISH"}` 来结束。
2. **重试最大次数卡点**：如果它在一个坏掉的接口上死钻牛角尖，重试（`max_retries`）达到极值（如 3 次），强制进入 Fail Fast 模式。
3. **金钱与耗时硬门限**：设定单次 Flow 会话的硬性 `max_tokens`（例如 8000 Tokens上限）。

**💡 超越点 (Tech Lead 视界)**
“我们团队吃过 API 疯狂报错导致的资金亏损大亏。从那次事故后，我在系统底座的最深内核处埋下了一根 **Token Budget 导火索**。每一次系统循环都在严格监控。不管大模型业务逻辑写得多么繁重，一旦累积 Token 撞到了预算红线，我的底层守护线程会直接极其生硬地执行 `Terminate Execution`，不管上面任务完没完成都强杀，以此捍卫业务成本的红线。”

## 高级问题 (Advanced)

### Q6（高级）为什么说“Agent 并不是大模型本身，而是 大模型 + 状态变迁 + 工具 + 控制循环（Control Loop）”？你如何真正在工程中实现这个循环？

**考察点**
- 把抽象概念落到“状态机、调度器编排”上的具象能力。
- 回答中是否含有核心架构级代码层面的经验。

**参考答案：底层机理拆解**
打个比方，大模型不是 Agent 本身，而仅仅是 Agent 用于处理模糊意图的 **“CPU (中央处理器)”**。单纯的大模型不具备自我驱动力，必须由外部系统为它提供“时钟频率”和运行底板。
它的实现依赖这四个核心：
1. **状态变迁 (State Machine)**：用作跟踪当前节点的健康指数与流转位面（比如将 `Running` 切换到 `Suspended` 或 `Completed`）。
2. **工具容器**：负责与物理世界的真实 I/O 交互，用高确定的网络请求验证 AI 模型高模糊的假设。
3. **控制循环**：在执行层（Runtime）实现。通常是一个高健壮性的 `try-catch` 加上带 `Task Queue` (任务队列) 的死循环（如 `while (!done)` 主循环）。在这个大循环中，AI 的输出被捕获并决定下一步抛向哪里。

**💡 超越点 (Tech Lead 视界)**
“我把这套由大模型决策、但由底层系统掌握流转边界的结构，通过强大的 **DurableScheduler (持久化编排器)** 写到了极致。在一个有向无环图 (DAG) 工作流内，只要我们每跨过一个环节节点，底座就会把此时的数据状态快照写入关系数据库（Checkpointing）。这带来的降维打击是：一旦中途因为高并发 OOM (内存溢出) 导致整个系统崩溃，服务重启的刹那，系统能瞬间接盘上次的快照，完美闭合控制循环。”

## 进阶硬核问题 (Expert)

### Q7（进阶）从自动驾驶的 L2 (辅助巡航) 向上跨越到 L4 (无人自治)，如果对应在商业应用级的 Agent ，中间最大的技术鸿沟及底层突破在哪里？

**考察点**
- 顶层设计视野：评估候选人在复杂 AI/Agent 环境下，关于自动降级、回退兜底机制（Fallback）和红蓝对抗意识。

**参考答案：工程治理深渊**
在构建 L2 辅助系统（如 Copilot、智能问答助手）时，即便它满级幻觉乱说一气，最后**由于有一个人类“坐在副驾驶”上**人工点击“发送/批准”，灾难总是能在最后关头被拦截。
但进入到自动跑批的 **L4 完全自治智能体** (例如深夜自动化重读数据库并群发给上百个供货商砍价)，缺少了最后的这道“人智兜底（Human-in-the-loop）拦网”。这就暴露出以下鸿沟：

1. **环境非共识（Environment Misalignment）**：因为没有人去看它获取的数据了，一旦第一环取得错误数据并下发给下一个级联 Agent，错误污染被呈指数级放大，最后结果灾难化收场。
2. **多态拓扑（Dynamic Topology）应对**：在无人干预时，环境往往不可预期。如果固化的代码图走不通了，系统不能像 L2 一样发个红框报错，它必须能自己根据现场“长出新的寻路逻辑支路”。

**💡 超越点 (Tech Lead 视界)**
“所以，构建属于我们平台的企业级 L4 基石，不是指望再出一个更牛逼的大模型，而是必须在系统层引入 **Meta-Agent (主控母体) 的反思裂变功能**。当出现环境阻滞，主控模块能挂起挂掉的分支，重新根据 `Evaluation Schema`（评测格式限制）原地撕掉这部分执行图，‘无性生殖’出其他的补救 Todo 去兜圈子验证。只有当它的确已经黔驴技穷时，它才会调用系统终极方案：强制中断全自动流程，在终端拉警报触发 Hand-off (人工接管)。这就是我们的容灾工程哲学。”
